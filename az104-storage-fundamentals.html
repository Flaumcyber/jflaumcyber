// why these choices

Redundancy: why LRS

Azure offers four main redundancy tiers, each trading cost for durability. LRS (Locally Redundant Storage) copies data three times within a single datacenter, protecting against hardware failure but not a datacenter or regional outage. ZRS (Zone-Redundant) spreads those three copies across separate availability zones in the same region, protecting against a datacenter-level failure at a higher cost. GRS (Geo-Redundant) adds asynchronous replication to a paired secondary region, protecting against a regional disaster, at a further cost increase. GZRS combines zone and geo redundancy for the highest durability and the highest price.

LRS was the right choice here because this is disposable lab data that gets rebuilt from Terraform and Bicep definitions checked into this repo. If the datacenter hosting it disappeared entirely, the fix is redeploying the code, not restoring from a geo-replicated copy. Paying for ZRS or GRS protection on data that costs nothing to regenerate would be optimizing for a failure mode that doesn't actually threaten anything important here.

Access tier: why Hot to Cool, not Archive

Hot tier has the highest storage cost and the lowest access cost, built for data touched frequently. Cool tier lowers the storage cost in exchange for a higher access cost and an expected minimum retention around 30 days, built for data accessed occasionally but not urgently, like older logs or infrequently opened backups. Archive tier drops storage cost to the lowest point but requires an explicit rehydration step, taking hours, before the data can be read again at all.

Cool was the right comparison point for this lab rather than Archive, because the goal was to demonstrate the tier mechanism and its immediate effect on a blob's properties. Cool still allows instant reads, so the change was visible and verifiable in the same session. Archive would have required a rehydration wait that doesn't teach anything additional about how tiering itself works, and realistically matches fewer scenarios than Cool does for data someone might still want to open on short notice.

// what i built

Steps

First real Storage-domain build, including a real mistake caught and fixed mid-lab.

  • Created the rg-az104-storage resource group
  • Created a Standard performance, LRS-redundant storage account, az104storagejf
  • Created a private blob container, az104-storage-blob1
  • Uploaded a real file, baby-yoda-2021.jpeg, which landed in the Hot tier by default
  • Changed the blob's access tier from Hot to Cool and confirmed the update
Note: The storage account was accidentally created inside rg-az104-identity instead of rg-az104-storage. Caught it by checking the Essentials panel, then used Azure's built-in resource Move feature to relocate it without deleting and rebuilding anything.
Follow-up: This mixup happened in the same resource group I nearly deleted by accident during this same study session. Between the two, rg-az104-identity got a permanent CanNotDelete lock reapplied afterward, this time for real protection rather than as a Lab 1.4 demonstration.

// infrastructure as code

"If you can build it again tomorrow without looking at yesterday's code, you've learned it. If you need to copy and paste it again, you've only completed a tutorial."

I am learning Infrastructure as Code deliberately, specifically Terraform and Bicep, rather than treating them as copy-paste snippets. The code below reflects actual understanding of each resource, not just reproduced boilerplate.

Terraform .tf

# main.tf resource "azurerm_resource_group" "storage" { name = "rg-az104-storage" location = "eastus" } resource "azurerm_storage_account" "az104storagejf" { name = "az104storagejf" resource_group_name = azurerm_resource_group.storage.name location = azurerm_resource_group.storage.location account_tier = "Standard" account_replication_type = "LRS" account_kind = "StorageV2" } resource "azurerm_storage_container" "blob_container" { name = "az104-storage-blob1" storage_account_name = azurerm_storage_account.az104storagejf.name container_access_type = "private" } resource "azurerm_storage_blob" "test_blob" { name = "baby-yoda-2021.jpeg" storage_account_name = azurerm_storage_account.az104storagejf.name storage_container_name = azurerm_storage_container.blob_container.name type = "Block" source = "./baby-yoda-2021.jpeg" access_tier = "Cool" }

Bicep .bicep

Storage accounts, containers, and even blob metadata are all native ARM resource types, so the full chain from account down to access tier can be expressed directly in Bicep. Actual file upload still requires the CLI, PowerShell, or portal, since Bicep deploys infrastructure, not file contents.

// main.bicep resource storageAccount 'Microsoft.Storage/storageAccounts@2023-01-01' = { name: 'az104storagejf' location: resourceGroup().location sku: { name: 'Standard_LRS' } kind: 'StorageV2' properties: {} } resource blobService 'Microsoft.Storage/storageAccounts/blobServices@2023-01-01' = { parent: storageAccount name: 'default' } resource container 'Microsoft.Storage/storageAccounts/blobServices/containers@2023-01-01' = { parent: blobService name: 'az104-storage-blob1' properties: { publicAccess: 'None' } }
// command line

PowerShell

# Connect first: Connect-AzAccount New-AzResourceGroup -Name "rg-az104-storage" -Location "East US" New-AzStorageAccount -ResourceGroupName "rg-az104-storage" ` -Name "az104storagejf" ` -Location "East US" ` -SkuName "Standard_LRS" ` -Kind "StorageV2" $ctx = (Get-AzStorageAccount -ResourceGroupName "rg-az104-storage" -Name "az104storagejf").Context New-AzStorageContainer -Name "az104-storage-blob1" -Context $ctx -Permission Off Set-AzStorageBlobContent -File ".\baby-yoda-2021.jpeg" ` -Container "az104-storage-blob1" ` -Blob "baby-yoda-2021.jpeg" ` -Context $ctx # Change access tier to Cool $blob = Get-AzStorageBlob -Container "az104-storage-blob1" -Blob "baby-yoda-2021.jpeg" -Context $ctx $blob.ICloudBlob.SetStandardBlobTier("Cool")

Azure CLI

# Sign in first: az login az group create --name rg-az104-storage --location eastus az storage account create \ --name az104storagejf \ --resource-group rg-az104-storage \ --location eastus \ --sku Standard_LRS \ --kind StorageV2 az storage container create \ --name az104-storage-blob1 \ --account-name az104storagejf \ --public-access off az storage blob upload \ --account-name az104storagejf \ --container-name az104-storage-blob1 \ --name baby-yoda-2021.jpeg \ --file ./baby-yoda-2021.jpeg # Change access tier to Cool az storage blob set-tier \ --account-name az104storagejf \ --container-name az104-storage-blob1 \ --name baby-yoda-2021.jpeg \ --tier Cool
// what i learned
  • Always verify the resource group during creation, not after. The portal's create-resource flow lets the resource group field default to whatever was last used, which is exactly how this storage account ended up in rg-az104-identity. A quick glance at that field before clicking Create would have caught it immediately.
  • Resources can be moved between resource groups without being rebuilt. Azure's Move feature handled the correction cleanly, no data loss, no downtime, no need to delete and recreate the storage account from scratch.
  • New blobs default to whatever access tier the storage account has set, which was Hot here. Cool and Archive are opt-in per blob (or set as the account default), not something Azure assumes you want for older or less-accessed data.
