RBAC: Built-In vs. Custom Roles
Domain: Identities and Governance · AZ-104 █
// about

Assigning a built-in Reader role directly to a user, then building and assigning a custom role scoped down to exactly three permissions: read, start, and restart on virtual machines, with no delete or write access anywhere. This builds on Lab 1.1's group-based Reader assignment by adding the direct-assignment and custom-role patterns to the same resource group.

Resource Group: rg-az104-identity Microsoft Entra ID Custom RBAC Roles

// what i built

Steps

Built out the direct-assignment and custom-role patterns to contrast against the group-based Reader assignment from Lab 1.1.

  • Assigned the built-in Reader role directly to asmith at the rg-az104-identity scope, rather than through a group, to have a direct comparison point
  • Created a custom role named VM Restart Operator with exactly three actions: read, start, and restart on virtual machines
  • Deliberately left out the delete action and any write actions, so the role can never remove or reconfigure a VM, only read its state and start or restart it
  • Assigned the custom role directly to jdoe at the same resource group scope
  • Verified with Check access that jdoe now shows two separate assignments: Reader (inherited via the group from Lab 1.1) and VM Restart Operator (direct)
Note: Azure custom roles use an allow-list model. Leaving delete out of the actions array is what restricts it; there was no need to explicitly add it to notActions, since anything not listed in actions is denied by default.

// infrastructure as code

"If you can build it again tomorrow without looking at yesterday's code, you've learned it. If you need to copy and paste it again, you've only completed a tutorial."

I am learning Infrastructure as Code deliberately, specifically Terraform and Bicep, rather than treating them as copy-paste snippets. The code below reflects actual understanding of each resource, not just reproduced boilerplate.

Terraform .tf

# main.tf data "azuread_user" "asmith" { user_principal_name = "asmith@jflaum.onmicrosoft.com" } data "azuread_user" "jdoe" { user_principal_name = "jdoe@jflaum.onmicrosoft.com" } # Built-in Reader, assigned directly (no group) resource "azurerm_role_assignment" "asmith_reader" { scope = azurerm_resource_group.identity.id role_definition_name = "Reader" principal_id = data.azuread_user.asmith.object_id } # Custom role: read, start, restart only, no delete resource "azurerm_role_definition" "vm_restart_operator" { name = "VM Restart Operator" scope = azurerm_resource_group.identity.id description = "Can read, start, and restart virtual machines. Cannot delete." permissions { actions = [ "Microsoft.Compute/virtualMachines/read", "Microsoft.Compute/virtualMachines/start/action", "Microsoft.Compute/virtualMachines/restart/action" ] not_actions = [] } assignable_scopes = [ azurerm_resource_group.identity.id ] } resource "azurerm_role_assignment" "jdoe_vm_restart" { scope = azurerm_resource_group.identity.id role_definition_id = azurerm_role_definition.vm_restart_operator.role_definition_resource_id principal_id = data.azuread_user.jdoe.object_id }

Bicep .bicep

Custom role definitions and role assignments are native ARM resource types, so both are fully expressible in Bicep. The object IDs for asmith and jdoe are passed in as parameters, resolved ahead of time through the CLI or portal.

// main.bicep param asmithObjectId string param jdoeObjectId string // Built-in Reader role ID (same for every tenant) var readerRoleId = subscriptionResourceId('Microsoft.Authorization/roleDefinitions', 'acdd72a7-3385-48ef-bd42-f606fba81ae7') resource asmithReaderAssignment 'Microsoft.Authorization/roleAssignments@2022-04-01' = { name: guid(resourceGroup().id, asmithObjectId, 'Reader') properties: { principalId: asmithObjectId roleDefinitionId: readerRoleId principalType: 'User' } } resource vmRestartOperator 'Microsoft.Authorization/roleDefinitions@2022-04-01' = { name: guid('VM Restart Operator', resourceGroup().id) properties: { roleName: 'VM Restart Operator' description: 'Can read, start, and restart virtual machines. Cannot delete.' type: 'CustomRole' permissions: [ { actions: [ 'Microsoft.Compute/virtualMachines/read' 'Microsoft.Compute/virtualMachines/start/action' 'Microsoft.Compute/virtualMachines/restart/action' ] notActions: [] } ] assignableScopes: [ resourceGroup().id ] } } resource jdoeCustomRoleAssignment 'Microsoft.Authorization/roleAssignments@2022-04-01' = { name: guid(resourceGroup().id, jdoeObjectId, vmRestartOperator.id) properties: { principalId: jdoeObjectId roleDefinitionId: vmRestartOperator.id principalType: 'User' } }
// command line

PowerShell

# Connect first: Connect-AzAccount # Assign built-in Reader directly to asmith New-AzRoleAssignment -SignInName "asmith@jflaum.onmicrosoft.com" ` -RoleDefinitionName "Reader" ` -ResourceGroupName "rg-az104-identity" # Build the custom role from a copy of an existing definition $role = Get-AzRoleDefinition -Name "Reader" $role.Id = $null $role.Name = "VM Restart Operator" $role.Description = "Can read, start, and restart virtual machines. Cannot delete." $role.IsCustom = $true $role.Actions.Clear() $role.Actions.Add("Microsoft.Compute/virtualMachines/read") $role.Actions.Add("Microsoft.Compute/virtualMachines/start/action") $role.Actions.Add("Microsoft.Compute/virtualMachines/restart/action") $role.AssignableScopes.Clear() $role.AssignableScopes.Add("/subscriptions/<subscription-id>/resourceGroups/rg-az104-identity") New-AzRoleDefinition -Role $role # Assign the custom role to jdoe New-AzRoleAssignment -SignInName "jdoe@jflaum.onmicrosoft.com" ` -RoleDefinitionName "VM Restart Operator" ` -ResourceGroupName "rg-az104-identity"

Azure CLI

# Sign in first: az login # Assign built-in Reader directly to asmith az role assignment create \ --assignee asmith@jflaum.onmicrosoft.com \ --role "Reader" \ --resource-group rg-az104-identity # Create the custom role from a JSON definition az role definition create --role-definition '{ "Name": "VM Restart Operator", "Description": "Can read, start, and restart virtual machines. Cannot delete.", "Actions": [ "Microsoft.Compute/virtualMachines/read", "Microsoft.Compute/virtualMachines/start/action", "Microsoft.Compute/virtualMachines/restart/action" ], "NotActions": [], "AssignableScopes": ["/subscriptions/<subscription-id>/resourceGroups/rg-az104-identity"] }' # Assign the custom role to jdoe az role assignment create \ --assignee jdoe@jflaum.onmicrosoft.com \ --role "VM Restart Operator" \ --resource-group rg-az104-identity
// what i learned
  • Custom roles use an allow-list model, not a deny-list one. Leaving delete out of the actions array was enough to block it; notActions is for carving exceptions out of a wildcard grant, not something that had to be populated here.
  • assignableScopes is what actually limits where a custom role can be used. Scoping it to just rg-az104-identity means this role cannot be assigned anywhere else in the subscription, even by someone with Owner access, without editing the role definition itself.
  • A single user can hold both a group-inherited role and a direct assignment at the same time. jdoe's Check access result showed Reader (via sg-az104-readers) and VM Restart Operator (direct) side by side, which is exactly the kind of layered access the exam expects you to be able to read and reason about.
