// why these choices

The portal instead of CLI, for this lab specifically

Container Apps' portal wizard combines environment creation and app deployment into a single guided flow, which made it a genuinely better first-exposure path than the CLI equivalent, which requires several separate commands and more upfront knowledge of the resource model. The CLI and PowerShell equivalents are documented below and are the intended path for revisiting this lab after the full AZ-104 series is complete.

Microsoft's quickstart image instead of a custom container

Using mcr.microsoft.com/azuredocs/containerapps-helloworld:latest kept this lab focused on Container Apps as a compute and scaling platform, rather than turning it into a container registry and image-build lab as well. Azure Container Registry and custom image builds are a natural extension for a later, dedicated lab.

Min replicas of 0, left at its default rather than raised

This is the single clearest technical distinction from Lab 3.3's VM Scale Set, which always keeps at least its minimum instance count running and billing. Leaving min replicas at 0 here demonstrates the actual value proposition of serverless containers directly, rather than describing it abstractly: this app can scale down to genuinely zero running compute when idle, something no VM-based option in this domain can do.

Steps

Deployed environment and app together through the portal wizard, then verified live traffic, scaling configuration, and revision history.

  • Confirmed the Microsoft.App resource provider was registered on the subscription
  • Created rg-az104-containerapps in East US 2
  • Created cae-az104-demo (Container Apps Environment) and ca-az104-demo (Container App) together via the portal's combined creation wizard, using the built-in quickstart hello-world image with ingress enabled on port 80
  • Noted the auto-created Log Analytics workspace (workspacergaz104containerapps8d2a), required by the environment for logging
  • Confirmed the app's status as Running and loaded its live public Application Url in a browser, seeing the hello-world page render
  • Reviewed the Scale blade: min replicas 0, max replicas 10, an http-scaler rule already attached
  • Reviewed Revisions and replicas, confirming one active revision running
  • Deleted rg-az104-containerapps in full, removing the app, environment, and workspace together

// infrastructure as code

"If you can build it again tomorrow without looking at yesterday's code, you've learned it. If you need to copy and paste it again, you've only completed a tutorial."

I am learning Infrastructure as Code deliberately, specifically Terraform and Bicep, rather than treating them as copy-paste snippets. This lab was built through the portal, so the code below is the deliberate as-code equivalent of what the wizard did, written to understand the resource model, not copied from a generated template.

Terraform .tf

# main.tf resource "azurerm_resource_group" "containerapps" { name = "rg-az104-containerapps" location = "eastus2" } resource "azurerm_log_analytics_workspace" "demo" { name = "law-az104-containerapps" location = azurerm_resource_group.containerapps.location resource_group_name = azurerm_resource_group.containerapps.name sku = "PerGB2018" retention_in_days = 30 } resource "azurerm_container_app_environment" "demo" { name = "cae-az104-demo" location = azurerm_resource_group.containerapps.location resource_group_name = azurerm_resource_group.containerapps.name log_analytics_workspace_id = azurerm_log_analytics_workspace.demo.id } resource "azurerm_container_app" "demo" { name = "ca-az104-demo" container_app_environment_id = azurerm_container_app_environment.demo.id resource_group_name = azurerm_resource_group.containerapps.name revision_mode = "Single" template { min_replicas = 0 max_replicas = 10 container { name = "containerapps-helloworld" image = "mcr.microsoft.com/azuredocs/containerapps-helloworld:latest" cpu = 0.25 memory = "0.5Gi" } } ingress { external_enabled = true target_port = 80 traffic_weight { percentage = 100 latest_revision = true } } }

Bicep .bicep

Bicep's resource model mirrors what the portal wizard actually created step for step: a Log Analytics workspace, a Container Apps environment tied to it, and the app itself referencing the environment and defining its own scale and ingress rules.

// main.bicep resource logAnalytics 'Microsoft.OperationalInsights/workspaces@2023-09-01' = { name: 'law-az104-containerapps' location: 'eastus2' properties: { sku: { name: 'PerGB2018' } retentionInDays: 30 } } resource containerAppEnv 'Microsoft.App/managedEnvironments@2023-05-01' = { name: 'cae-az104-demo' location: 'eastus2' properties: { appLogsConfiguration: { destination: 'log-analytics' logAnalyticsConfiguration: { customerId: logAnalytics.properties.customerId sharedKey: logAnalytics.listKeys().primarySharedKey } } } } resource containerApp 'Microsoft.App/containerApps@2023-05-01' = { name: 'ca-az104-demo' location: 'eastus2' properties: { managedEnvironmentId: containerAppEnv.id configuration: { ingress: { external: true targetPort: 80 } } template: { containers: [ { name: 'containerapps-helloworld' image: 'mcr.microsoft.com/azuredocs/containerapps-helloworld:latest' resources: { cpu: json('0.25') memory: '0.5Gi' } } ] scale: { minReplicas: 0 maxReplicas: 10 } } } }
// command line

PowerShell

# Connect first: Connect-AzAccount # Note: this lab was built via portal; commands below are the equivalent path for a future revisit New-AzResourceGroup -Name "rg-az104-containerapps" -Location "East US 2" # Az.App module handles Container Apps New-AzContainerAppManagedEnv -EnvName "cae-az104-demo" ` -ResourceGroupName "rg-az104-containerapps" -Location "East US 2" New-AzContainerApp -Name "ca-az104-demo" -ResourceGroupName "rg-az104-containerapps" ` -Location "East US 2" -ManagedEnvironmentId (Get-AzContainerAppManagedEnv -EnvName "cae-az104-demo" -ResourceGroupName "rg-az104-containerapps").Id ` -TemplateContainer @{ Name = "containerapps-helloworld"; Image = "mcr.microsoft.com/azuredocs/containerapps-helloworld:latest" } ` -IngressExternal $true -IngressTargetPort 80 # Confirm status (Get-AzContainerApp -Name "ca-az104-demo" -ResourceGroupName "rg-az104-containerapps").ProvisioningState

Azure CLI

# Sign in first: az login az provider register --namespace Microsoft.App az provider show --namespace Microsoft.App --query "registrationState" -o tsv az group create --resource-group rg-az104-containerapps --location eastus2 # containerapp extension installs automatically on first use if missing az containerapp env create \ --name cae-az104-demo \ --resource-group rg-az104-containerapps \ --location eastus2 az containerapp create \ --name ca-az104-demo \ --resource-group rg-az104-containerapps \ --environment cae-az104-demo \ --image mcr.microsoft.com/azuredocs/containerapps-helloworld:latest \ --target-port 80 \ --ingress external \ --min-replicas 0 \ --max-replicas 10 # Confirm live and get the public URL az containerapp show --name ca-az104-demo --resource-group rg-az104-containerapps --query "properties.configuration.ingress.fqdn" -o tsv # Clean up, full resource group (removes app, environment, and Log Analytics workspace) az group delete --name rg-az104-containerapps --yes --no-wait
// what i learned
  • Container Apps environments require a Log Analytics workspace, and it's created automatically. This isn't optional infrastructure the way an NSG or public IP can sometimes be skipped, it's a hard dependency for logging. Worth remembering it exists for teardown purposes even though deleting the resource group handles it automatically.
  • Scaling to zero is a genuinely different cost model, not just a smaller number. A VM Scale Set's minimum replica count is still whole VMs, each billing continuously. A Container App with min replicas set to 0 can have zero running compute and zero compute cost during idle periods, only scaling up (and only billing) when traffic actually arrives. That's the real distinction between "elastic" and "serverless."
  • The portal's combined environment-and-app wizard is a genuinely good learning path for a first exposure to a new Azure service. Seeing environment creation and app deployment happen together in one guided flow, rather than as separate CLI commands run in sequence, made the relationship between the two resource types clearer than reading documentation about them would have.
  • Revisions exist from the very first deployment, not just after an update. Even a single, never-updated Container App already has a named revision (ca-az104-demo--lpewvfn in this case). Understanding that a revision is Container Apps' fundamental unit of deployment, not an optional versioning feature you opt into later, matters for how blue-green deployments and traffic splitting work in future labs.
