Entra ID Users, Groups, and Group-Based RBAC
Domain: Manage Identities and Governance · AZ-104 █
// about

Creating Microsoft Entra ID users, organizing them into a security group, and assigning a role to the group rather than to individuals. This is the identity foundation the rest of the AZ-104 labs build on, and the group-based pattern is the practice tested most directly in the Identities and Governance domain.

Resource Group: rg-az104-identity Microsoft Entra ID RBAC

// what i built

Steps

Built out identity and access management using the group-based pattern instead of assigning roles directly to users.

  • Created two test users in Entra ID: jdoe and asmith
  • Created a security group named sg-az104-readers and added both users as members
  • Assigned the built-in Reader role to the group at the resource group scope, rather than assigning it to each user individually
  • Verified the assignment using Check access in the Azure portal for one of the member users
Note: Assigning roles to groups instead of individual users is the recommended practice because it scales. Adding or removing a user from the group changes their access automatically, without touching the role assignment itself.

I am learning Infrastructure as Code deliberately, specifically Terraform and Bicep, rather than treating them as copy-paste snippets. The code below reflects actual understanding of each resource, not just reproduced boilerplate.

Terraform .tf

# main.tf # Requires the azuread and azurerm providers terraform { required_providers { azuread = { source = "hashicorp/azuread" version = "~> 2.0" } azurerm = { source = "hashicorp/azurerm" version = "~> 3.0" } } } provider "azuread" {} provider "azurerm" { features {} } # Users resource "azuread_user" "jdoe" { user_principal_name = "jdoe@jflaum.onmicrosoft.com" display_name = "J Doe" password = "ChangeMe123!" } resource "azuread_user" "asmith" { user_principal_name = "asmith@jflaum.onmicrosoft.com" display_name = "A Smith" password = "ChangeMe123!" } # Security group resource "azuread_group" "readers" { display_name = "sg-az104-readers" security_enabled = true } resource "azuread_group_member" "jdoe_member" { group_object_id = azuread_group.readers.object_id member_object_id = azuread_user.jdoe.object_id } resource "azuread_group_member" "asmith_member" { group_object_id = azuread_group.readers.object_id member_object_id = azuread_user.asmith.object_id } # Resource group and group-based role assignment resource "azurerm_resource_group" "identity" { name = "rg-az104-identity" location = "eastus" } resource "azurerm_role_assignment" "readers_reader" { scope = azurerm_resource_group.identity.id role_definition_name = "Reader" principal_id = azuread_group.readers.object_id }

Bicep .bicep

Entra ID users and groups are managed through Microsoft Graph rather than Azure Resource Manager, so Bicep is used here only for the resource group and the role assignment. The group itself is created ahead of time through the Azure CLI or PowerShell, and its object ID is passed in as a parameter.

// main.bicep // Deploys the resource group scope role assignment // The security group must already exist; pass its object ID as a parameter targetScope = 'subscription' param location string = 'eastus' param readersGroupObjectId string resource identityRg 'Microsoft.Resources/resourceGroups@2023-07-01' = { name: 'rg-az104-identity' location: location } module readerAssignment 'roleAssignment.bicep' = { name: 'readerAssignment' scope: identityRg params: { principalId: readersGroupObjectId roleDefinitionId: subscriptionResourceId('Microsoft.Authorization/roleDefinitions', 'acdd72a7-3385-48ef-bd42-f606fba81ae7') } } // roleAssignment.bicep param principalId string param roleDefinitionId string resource roleAssignment 'Microsoft.Authorization/roleAssignments@2022-04-01' = { name: guid(resourceGroup().id, principalId, roleDefinitionId) properties: { principalId: principalId roleDefinitionId: roleDefinitionId principalType: 'Group' } }
// command line

PowerShell

# Requires the Microsoft.Graph and Az PowerShell modules # Connect first: Connect-MgGraph -Scopes "User.ReadWrite.All","Group.ReadWrite.All" # Connect-AzAccount # Create users $PasswordProfile = @{ Password = "ChangeMe123!" } New-MgUser -DisplayName "J Doe" ` -UserPrincipalName "jdoe@jflaum.onmicrosoft.com" ` -MailNickname "jdoe" ` -AccountEnabled ` -PasswordProfile $PasswordProfile New-MgUser -DisplayName "A Smith" ` -UserPrincipalName "asmith@jflaum.onmicrosoft.com" ` -MailNickname "asmith" ` -AccountEnabled ` -PasswordProfile $PasswordProfile # Create the security group $Group = New-MgGroup -DisplayName "sg-az104-readers" ` -MailEnabled:$false ` -MailNickname "sgaz104readers" ` -SecurityEnabled # Add both users as members $JDoe = Get-MgUser -Filter "userPrincipalName eq 'jdoe@jflaum.onmicrosoft.com'" $ASmith = Get-MgUser -Filter "userPrincipalName eq 'asmith@jflaum.onmicrosoft.com'" New-MgGroupMember -GroupId $Group.Id -DirectoryObjectId $JDoe.Id New-MgGroupMember -GroupId $Group.Id -DirectoryObjectId $ASmith.Id # Assign Reader at the resource group scope, to the group New-AzRoleAssignment -ObjectId $Group.Id ` -RoleDefinitionName "Reader" ` -ResourceGroupName "rg-az104-identity"

Azure CLI

# Sign in first: az login # Create users az ad user create \ --display-name "J Doe" \ --user-principal-name jdoe@jflaum.onmicrosoft.com \ --password "ChangeMe123!" \ --force-change-password-next-sign-in true az ad user create \ --display-name "A Smith" \ --user-principal-name asmith@jflaum.onmicrosoft.com \ --password "ChangeMe123!" \ --force-change-password-next-sign-in true # Create the security group az ad group create \ --display-name "sg-az104-readers" \ --mail-nickname "sgaz104readers" # Add both users as members az ad group member add --group "sg-az104-readers" --member-id $(az ad user show --id jdoe@jflaum.onmicrosoft.com --query id -o tsv) az ad group member add --group "sg-az104-readers" --member-id $(az ad user show --id asmith@jflaum.onmicrosoft.com --query id -o tsv) # Assign Reader at the resource group scope, to the group GROUP_ID=$(az ad group show --group "sg-az104-readers" --query id -o tsv) az role assignment create \ --assignee-object-id "$GROUP_ID" \ --assignee-principal-type Group \ --role "Reader" \ --resource-group rg-az104-identity
// what i learned
  • Group-based RBAC scales better than per-user assignment. Adding or removing someone from the group changes their access automatically, and it keeps the role assignment list on the resource itself short and auditable.
  • Object IDs, not display names, are what role assignments actually reference. The portal shows friendly names, but every assignment under the hood is tied to an immutable object ID, which is why the CLI and PowerShell commands above resolve the group and users to their IDs before assigning anything.
  • Entra ID resources sit outside standard ARM/Bicep resource types. Bicep can assign roles to a group, but it cannot create the group itself without the Microsoft Graph Bicep extension, so the group has to exist first through the CLI, PowerShell, or the portal.
