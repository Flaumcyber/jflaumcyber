Subscriptions, Cost Management, and Resource Locks
Domain: Identities and Governance · AZ-104 █
// about

Two governance controls that protect a subscription from two different kinds of mistakes: a budget alert that catches unexpected spend before it grows, and a resource lock that blocks accidental deletion of a resource group entirely. Verified both by proving the lock actually stops a real delete attempt, not just by assuming it would.

Scope: Subscription & Resource Group Cost Management Resource Locks

// what i built

Steps

Closed out the Identities and Governance domain by verifying two protective controls actually work, not just that they exist.

  • Reused the budget-az104-labs budget set up earlier: $180 amount, alerts at 50/75/90% of spend, on the billing account scope
  • Applied a CanNotDelete lock named prevent-delete-identity-rg to rg-az104-identity, the resource group holding all four labs from this domain
  • Attempted to delete rg-az104-identity through the normal Delete resource group flow, and confirmed Azure blocked it with an explicit error naming the lock as the cause
  • Removed the lock afterward, confirmed via the Locks blade showing "This resource has no locks"
Note: A CanNotDelete lock still allows edits and new resources inside the scope; it only blocks deletion. That distinction from a ReadOnly lock matters both for the exam and for not accidentally freezing a resource group you still need to work in.

// infrastructure as code

"If you can build it again tomorrow without looking at yesterday's code, you've learned it. If you need to copy and paste it again, you've only completed a tutorial."

I am learning Infrastructure as Code deliberately, specifically Terraform and Bicep, rather than treating them as copy-paste snippets. The code below reflects actual understanding of each resource, not just reproduced boilerplate.

Terraform .tf

# main.tf data "azurerm_billing_account" "current" {} resource "azurerm_consumption_budget_billing_account" "az104_labs" { name = "budget-az104-labs" billing_account_id = data.azurerm_billing_account.current.id amount = 180 time_grain = "Monthly" time_period { start_date = "2026-08-01T00:00:00Z" } notification { enabled = true threshold = 50.0 operator = "GreaterThanOrEqualTo" contact_emails = ["jflaum.it@gmail.com"] } notification { enabled = true threshold = 75.0 operator = "GreaterThanOrEqualTo" contact_emails = ["jflaum.it@gmail.com"] } notification { enabled = true threshold = 90.0 operator = "GreaterThanOrEqualTo" contact_emails = ["jflaum.it@gmail.com"] } } resource "azurerm_management_lock" "prevent_delete_identity_rg" { name = "prevent-delete-identity-rg" scope = azurerm_resource_group.identity.id lock_level = "CanNotDelete" notes = "Cannot Delete Resource Group" }

Bicep .bicep

Resource locks are a native ARM resource type scoped to whatever resource they protect. Budgets, like the policy assignment in Lab 1.3, target the billing account or subscription rather than a resource group.

// main.bicep resource identityRgLock 'Microsoft.Authorization/locks@2020-05-01' = { name: 'prevent-delete-identity-rg' scope: resourceGroup() properties: { level: 'CanNotDelete' notes: 'Cannot Delete Resource Group' } }
// command line

PowerShell

# Connect first: Connect-AzAccount # Apply a CanNotDelete lock to the resource group New-AzResourceLock -LockName "prevent-delete-identity-rg" ` -LockLevel CanNotDelete ` -LockNotes "Cannot Delete Resource Group" ` -ResourceGroupName "rg-az104-identity" # Confirm it exists Get-AzResourceLock -ResourceGroupName "rg-az104-identity" # This will fail while the lock is in place Remove-AzResourceGroup -Name "rg-az104-identity" -Force # Remove the lock afterward Remove-AzResourceLock -LockName "prevent-delete-identity-rg" ` -ResourceGroupName "rg-az104-identity" -Force

Azure CLI

# Sign in first: az login # Apply a CanNotDelete lock to the resource group az lock create \ --name prevent-delete-identity-rg \ --lock-type CanNotDelete \ --notes "Cannot Delete Resource Group" \ --resource-group rg-az104-identity # Confirm it exists az lock list --resource-group rg-az104-identity -o table # This will fail while the lock is in place az group delete --name rg-az104-identity --yes # Remove the lock afterward az lock delete --name prevent-delete-identity-rg --resource-group rg-az104-identity
// what i learned
  • CanNotDelete is not the same as read-only. The lock blocked deletion of the resource group entirely, but I could still have edited tags, added resources, or changed IAM assignments inside it while the lock was active. A ReadOnly lock would have blocked that too.
  • Locks and budgets protect against different failure modes. A budget catches spend drifting somewhere unexpected; a lock catches a person, script, or automated cleanup accidentally deleting something that's still in use. Neither substitutes for the other.
  • The delete error names the specific lock, not just a generic denial. That specificity matters in a real environment with many locks across many resource groups, since it tells you exactly what to go remove rather than making you hunt for the cause.
