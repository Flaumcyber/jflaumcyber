Access Control: SAS Tokens and Private Endpoints
Domain: Implement and Manage Storage · AZ-104 █
// about

Two different ways to control access to storage that solve two different problems. A SAS token grants scoped, time-limited authorization without ever sharing the storage account key. A private endpoint removes the storage account from the public internet entirely for a given network path. Built and tested both against the same storage account from Lab 2.1.

Resource Group: rg-az104-storage SAS Tokens Private Endpoints

// why these choices

SAS token, scoped to Read only, instead of the storage account key

The storage account key grants full read, write, and delete access to everything in the account, indefinitely, until manually rotated. A SAS token narrows that down to exactly one permission, on exactly one resource, for exactly one short window of time. If a SAS token leaks, the exposure is bounded: read access to one blob for a few hours. If the account key leaks, the exposure is the entire storage account, forever, until someone notices and rotates it. Scoping down to the minimum needed access is the whole reason SAS tokens exist as a separate mechanism from the key.

Private endpoint instead of a firewall rule on the public endpoint

A firewall rule on the storage account's public endpoint still leaves the storage account reachable from the public internet, just restricted to approved source IPs. A private endpoint removes the public attack surface for that connection path entirely: traffic from the VNet travels over Microsoft's private backbone network directly to the storage service and never touches the public internet. A firewall rule answers "who is allowed in the door." A private endpoint answers "there is no public door for this path at all."

Private subnet with no default outbound access

Chose "Enable private subnet (no default outbound access)" when creating snet-private-endpoints, since a private endpoint doesn't need to initiate outbound connections to the internet to function. Its job is letting resources inside the VNet reach the storage account privately, not the other way around. Leaving the subnet without default outbound access is tighter security posture for a subnet whose only purpose is hosting private endpoints, and it reinforces the same network isolation idea the private endpoint itself is built around.

// what i built

Steps

Built and tested the authorization layer first, then the network isolation layer, against the same storage account.

  • Generated a SAS token on baby-yoda-2021.jpeg scoped to Read only, with a short expiry, using the account key as the signing method
  • Confirmed the SAS URL loaded the blob directly, then stripped the token from the URL and confirmed the bare path returned PublicAccessNotPermitted, proving the container itself is still locked down and the token is what's actually granting access
  • Built a minimal VNet, vnet-az104-storage, with subnet snet-private-endpoints (10.0.0.0/24), configured as a private subnet with no default outbound access
  • Created a private endpoint targeting az104storagejf's blob sub-resource, linked to a private DNS zone (privatelink.blob.core.windows.net) so the storage account's normal hostname resolves to a private IP from inside the VNet
  • Verified the private endpoint's network interface actually received a real private IP address, 10.0.0.4, inside the subnet's range
Note: The private endpoint's name ended up as vnet-az104-storage instead of the planned pe-az104storagejf-blob; the name field appears to have carried over from the VNet earlier in the wizard. Left it as-is rather than deleting and recreating a resource that bills hourly just to fix a cosmetic name.
Note: Hit an empty Virtual network dropdown partway through creating the private endpoint. Cause was a region mismatch between the Basics tab and the VNet; private endpoints only list VNets in the same region they're being deployed to.

// infrastructure as code

"If you can build it again tomorrow without looking at yesterday's code, you've learned it. If you need to copy and paste it again, you've only completed a tutorial."

I am learning Infrastructure as Code deliberately, specifically Terraform and Bicep, rather than treating them as copy-paste snippets. The code below reflects actual understanding of each resource, not just reproduced boilerplate.

Terraform .tf

# main.tf # SAS tokens are generated, not deployed as resources, # so the Terraform side of this lab is the network isolation half resource "azurerm_virtual_network" "storage" { name = "vnet-az104-storage" address_space = ["10.0.0.0/16"] location = azurerm_resource_group.storage.location resource_group_name = azurerm_resource_group.storage.name } resource "azurerm_subnet" "private_endpoints" { name = "snet-private-endpoints" resource_group_name = azurerm_resource_group.storage.name virtual_network_name = azurerm_virtual_network.storage.name address_prefixes = ["10.0.0.0/24"] private_endpoint_network_policies = "Disabled" } resource "azurerm_private_dns_zone" "blob" { name = "privatelink.blob.core.windows.net" resource_group_name = azurerm_resource_group.storage.name } resource "azurerm_private_dns_zone_virtual_network_link" "blob" { name = "vnet-az104-storage-link" resource_group_name = azurerm_resource_group.storage.name private_dns_zone_name = azurerm_private_dns_zone.blob.name virtual_network_id = azurerm_virtual_network.storage.id } resource "azurerm_private_endpoint" "storage_blob" { name = "pe-az104storagejf-blob" location = azurerm_resource_group.storage.location resource_group_name = azurerm_resource_group.storage.name subnet_id = azurerm_subnet.private_endpoints.id private_service_connection { name = "psc-az104storagejf-blob" private_connection_resource_id = azurerm_storage_account.az104storagejf.id subresource_names = ["blob"] is_manual_connection = false } private_dns_zone_group { name = "default" private_dns_zone_ids = [azurerm_private_dns_zone.blob.id] } }

Bicep .bicep

Same structure as Terraform: VNet, subnet, private DNS zone, and the private endpoint itself, all native ARM resource types.

// main.bicep resource vnet 'Microsoft.Network/virtualNetworks@2023-09-01' = { name: 'vnet-az104-storage' location: resourceGroup().location properties: { addressSpace: { addressPrefixes: ['10.0.0.0/16'] } subnets: [ { name: 'snet-private-endpoints' properties: { addressPrefix: '10.0.0.0/24' privateEndpointNetworkPolicies: 'Disabled' } } ] } } resource privateDnsZone 'Microsoft.Network/privateDnsZones@2020-06-01' = { name: 'privatelink.blob.core.windows.net' location: 'global' } resource dnsZoneLink 'Microsoft.Network/privateDnsZones/virtualNetworkLinks@2020-06-01' = { parent: privateDnsZone name: 'vnet-az104-storage-link' location: 'global' properties: { virtualNetwork: { id: vnet.id } registrationEnabled: false } } resource privateEndpoint 'Microsoft.Network/privateEndpoints@2023-09-01' = { name: 'pe-az104storagejf-blob' location: resourceGroup().location properties: { subnet: { id: vnet.properties.subnets[0].id } privateLinkServiceConnections: [ { name: 'psc-az104storagejf-blob' properties: { privateLinkServiceId: resourceId('Microsoft.Storage/storageAccounts', 'az104storagejf') groupIds: ['blob'] } } ] } }
// command line

PowerShell

# Connect first: Connect-AzAccount # Generate a read-only SAS token, expires in 8 hours $ctx = (Get-AzStorageAccount -ResourceGroupName "rg-az104-storage" -Name "az104storagejf").Context $sasToken = New-AzStorageBlobSASToken -Container "az104-storage-blob1" ` -Blob "baby-yoda-2021.jpeg" ` -Permission "r" ` -ExpiryTime (Get-Date).AddHours(8) ` -Context $ctx # Network isolation half $vnet = New-AzVirtualNetwork -ResourceGroupName "rg-az104-storage" ` -Name "vnet-az104-storage" -Location "East US" -AddressPrefix "10.0.0.0/16" Add-AzVirtualNetworkSubnetConfig -Name "snet-private-endpoints" ` -VirtualNetwork $vnet -AddressPrefix "10.0.0.0/24" ` -PrivateEndpointNetworkPoliciesFlag "Disabled" | Set-AzVirtualNetwork $subnet = Get-AzVirtualNetworkSubnetConfig -Name "snet-private-endpoints" -VirtualNetwork $vnet $storageAccount = Get-AzStorageAccount -ResourceGroupName "rg-az104-storage" -Name "az104storagejf" $connection = New-AzPrivateLinkServiceConnection -Name "psc-az104storagejf-blob" ` -PrivateLinkServiceId $storageAccount.Id -GroupId "blob" New-AzPrivateEndpoint -ResourceGroupName "rg-az104-storage" ` -Name "pe-az104storagejf-blob" -Location "East US" ` -Subnet $subnet -PrivateLinkServiceConnection $connection

Azure CLI

# Sign in first: az login # Generate a read-only SAS token, expires in 8 hours EXPIRY=$(date -u -d "8 hours" '+%Y-%m-%dT%H:%MZ') az storage blob generate-sas \ --account-name az104storagejf \ --container-name az104-storage-blob1 \ --name baby-yoda-2021.jpeg \ --permissions r \ --expiry $EXPIRY \ --https-only # Network isolation half az network vnet create \ --resource-group rg-az104-storage \ --name vnet-az104-storage \ --address-prefix 10.0.0.0/16 \ --subnet-name snet-private-endpoints \ --subnet-prefix 10.0.0.0/24 az network private-dns zone create \ --resource-group rg-az104-storage \ --name privatelink.blob.core.windows.net az network private-dns link vnet create \ --resource-group rg-az104-storage \ --zone-name privatelink.blob.core.windows.net \ --name vnet-az104-storage-link \ --virtual-network vnet-az104-storage \ --registration-enabled false az network private-endpoint create \ --resource-group rg-az104-storage \ --name pe-az104storagejf-blob \ --vnet-name vnet-az104-storage \ --subnet snet-private-endpoints \ --private-connection-resource-id $(az storage account show --name az104storagejf --query id -o tsv) \ --group-id blob \ --connection-name psc-az104storagejf-blob
// what i learned
  • Authorization and network isolation are separate problems, often solved together. A SAS token controls who can do what. A private endpoint controls where the traffic is even allowed to originate from. A real production storage account would typically use both at once, not choose one over the other.
  • Private endpoints only show compatible VNets in the same region as the endpoint itself. The empty dropdown wasn't a bug, it was Azure correctly filtering out a region mismatch that I hadn't noticed on the Basics tab.
  • Not every mistake is worth fixing immediately. The private endpoint's misnamed resource still functions identically to a correctly-named one. Deleting and recreating a resource that bills hourly, purely to fix a label, would have cost more in time and money than the naming inconsistency itself.
