// about

The first lab in the Compute domain. Deployed a Linux and a Windows VM into a shared resource group, hit a real subscription-level regional quota restriction along the way, and configured auto-shutdown on both immediately rather than as an afterthought.

// why these choices

Standard_D2as_v7, once B-series proved unavailable

The original plan was Standard_B1s, a Burstable-tier size that stays inside Azure's free 750-hour monthly allowance and matches a lab VM's idle-most-of-the-time usage pattern well. When the entire B-series family returned NotAvailableForSubscription in East US, D2as_v7 became the practical choice: a genuinely available, still-small 2 vCPU general purpose size, at a real but low cost of roughly $0.09/hour rather than free. The tradeoff was accepting a small real cost in exchange for something that actually deploys, rather than continuing to hunt for a free-tier size that may not have existed for this subscription in this region at all.

East US 2 instead of continuing to troubleshoot East US

Once both a Burstable size and a D-series size returned the identical NotAvailableForSubscription error in East US, that pattern pointed to a regional restriction on the subscription itself rather than a size-specific quota problem. Switching regions tests that theory directly and, if correct, resolves every size issue at once instead of continuing to negotiate one size at a time against a restriction that isn't going to lift by picking a different SKU.

Auto-shutdown configured immediately, not after the fact

Every VM in this lab bills by the hour the moment it exists, unlike almost everything built in the Identities, Governance, and Storage domains. Setting auto-shutdown as the very next action after deployment, rather than something to remember later, turns a habit into a default. The $180 budget alert from the Identities domain is still the backstop, but auto-shutdown is the thing that actually prevents needing that backstop to fire in the first place.

// what i built

Steps

Deployed two VMs and worked through a real regional capacity issue along the way.

  • Created rg-az104-compute, the resource group for the entire Compute domain
  • Attempted to deploy vm-az104-linux at Standard_B1s in East US, and hit NotAvailableForSubscription on every size tried, both Burstable and D-series
  • Switched the deployment region to East US 2, where D2as_v7 deployed cleanly, and used that size and region for both VMs
  • Deployed vm-az104-linux (Ubuntu Server 24.04) and vm-az104-windows (Windows Server 2022 Datacenter), both Standard_D2as_v7
  • Set auto-shutdown on both to 9:00 PM Central immediately after each deployment, before leaving either VM unattended
Note: Standard_B1s and every other size tested in East US returned NotAvailableForSubscription, on both the Burstable and D-series families. This turned out to be a regional restriction on the subscription itself, not a per-size quota issue. Switching to East US 2 resolved it immediately.
Note: vm-az104-windows initially deployed into an auto-created resource group, vm-az104-windows_group, instead of rg-az104-compute. Caught it on the Essentials panel and used the Move feature to relocate it, same fix pattern as the storage account mixup back in Lab 2.1.

I am learning Infrastructure as Code deliberately, specifically Terraform and Bicep, rather than treating them as copy-paste snippets. The code below reflects actual understanding of each resource, not just reproduced boilerplate.

Terraform .tf

# main.tf resource "azurerm_resource_group" "compute" { name = "rg-az104-compute" location = "eastus2" } resource "azurerm_virtual_network" "compute" { name = "vnet-az104-compute" address_space = ["10.1.0.0/16"] location = azurerm_resource_group.compute.location resource_group_name = azurerm_resource_group.compute.name } resource "azurerm_subnet" "compute" { name = "snet-az104-compute" resource_group_name = azurerm_resource_group.compute.name virtual_network_name = azurerm_virtual_network.compute.name address_prefixes = ["10.1.0.0/24"] } # Linux VM resource "azurerm_linux_virtual_machine" "linux" { name = "vm-az104-linux" resource_group_name = azurerm_resource_group.compute.name location = azurerm_resource_group.compute.location size = "Standard_D2as_v7" admin_username = "azureuser" admin_ssh_key { username = "azureuser" public_key = file("~/.ssh/id_rsa.pub") } network_interface_ids = [azurerm_network_interface.linux.id] os_disk { caching = "ReadWrite" storage_account_type = "Premium_LRS" } source_image_reference { publisher = "Canonical" offer = "ubuntu-24_04-lts" sku = "server" version = "latest" } } # Windows VM resource "azurerm_windows_virtual_machine" "windows" { name = "vm-az104-windows" resource_group_name = azurerm_resource_group.compute.name location = azurerm_resource_group.compute.location size = "Standard_D2as_v7" admin_username = "azureadmin" admin_password = var.windows_admin_password network_interface_ids = [azurerm_network_interface.windows.id] os_disk { caching = "ReadWrite" storage_account_type = "Premium_LRS" } source_image_reference { publisher = "MicrosoftWindowsServer" offer = "WindowsServer" sku = "2022-datacenter-g2" version = "latest" } } # Auto-shutdown, both VMs resource "azurerm_dev_test_global_vm_shutdown_schedule" "linux" { virtual_machine_id = azurerm_linux_virtual_machine.linux.id location = azurerm_resource_group.compute.location enabled = true daily_recurrence_time = "2100" timezone = "Central Standard Time" notification_settings { enabled = false } }

Bicep .bicep

VM deployment in Bicep requires more explicit wiring than Terraform, since the VM, NIC, public IP, and OS disk are all separate resource declarations that reference each other by id.

// main.bicep resource linuxVm 'Microsoft.Compute/virtualMachines@2023-09-01' = { name: 'vm-az104-linux' location: 'eastus2' properties: { hardwareProfile: { vmSize: 'Standard_D2as_v7' } osProfile: { computerName: 'vm-az104-linux' adminUsername: 'azureuser' linuxConfiguration: { disablePasswordAuthentication: true ssh: { publicKeys: [ { path: '/home/azureuser/.ssh/authorized_keys' keyData: sshPublicKey } ] } } } storageProfile: { imageReference: { publisher: 'Canonical' offer: 'ubuntu-24_04-lts' sku: 'server' version: 'latest' } } networkProfile: { networkInterfaces: [ { id: linuxNic.id } ] } } } resource shutdownSchedule 'Microsoft.DevTestLab/schedules@2018-09-15' = { name: 'shutdown-computevm-vm-az104-linux' location: 'eastus2' properties: { status: 'Enabled' taskType: 'ComputeVmShutdownTask' dailyRecurrence: { time: '2100' } timeZoneId: 'Central Standard Time' targetResourceId: linuxVm.id } }

PowerShell

# Connect first: Connect-AzAccount New-AzResourceGroup -Name "rg-az104-compute" -Location "East US 2" # Linux VM $cred = Get-Credential -Message "Enter azureuser credentials" New-AzVM -ResourceGroupName "rg-az104-compute" -Name "vm-az104-linux" ` -Location "East US 2" -Image "Canonical:ubuntu-24_04-lts:server:latest" ` -Size "Standard_D2as_v7" -Credential $cred -GenerateSshKey # Windows VM $winCred = Get-Credential -Message "Enter azureadmin credentials" New-AzVM -ResourceGroupName "rg-az104-compute" -Name "vm-az104-windows" ` -Location "East US 2" -Image "MicrosoftWindowsServer:WindowsServer:2022-datacenter-g2:latest" ` -Size "Standard_D2as_v7" -Credential $winCred # Auto-shutdown, both VMs foreach ($vmName in @("vm-az104-linux", "vm-az104-windows")) { $props = @{ status = "Enabled" taskType = "ComputeVmShutdownTask" dailyRecurrence = @{ time = "2100" } timeZoneId = "Central Standard Time" targetResourceId = (Get-AzVM -ResourceGroupName "rg-az104-compute" -Name $vmName).Id notificationSettings = @{ status = "Disabled" } } New-AzResource -ResourceId "/subscriptions//resourceGroups/rg-az104-compute/providers/microsoft.devtestlab/schedules/shutdown-computevm-$vmName" ` -Properties $props -Force }

// what i learned
  • NotAvailableForSubscription can mean a regional restriction, not just a per-size quota gap. Testing a second, unrelated VM family (D-series after B-series) and getting the identical error was the actual diagnostic signal, not any single tooltip. Two different families failing the same way in the same region pointed at the region itself.
  • The VM creation form's Resource group field can silently default to an auto-generated name. Same root cause as the storage account mixup in Lab 2.1: not actively confirming a field before clicking Create is how a resource lands somewhere unintended. Azure's Move feature exists precisely because this is a common, recoverable mistake.
  • A VM's billing clock starts at deployment, not at first use. Configuring auto-shutdown as the literal next click after Create, rather than a task for later, is the only reliable way to guarantee it happens before an idle VM racks up unnecessary hours.
